# NOTES: работа с ассистентом

Работал с Claude Code в обоих репозиториях: `invest-pool-go` (API) и `invest-pool-react` (кабинет).

## Как была устроена работа

1. Решения о домене, деньгах, идемпотентности и правах я формулировал сам, до генерации кода (см. таблицу ниже). Claude
   получал их как ограничения, а не как вопрос «как лучше».
2. Claude писал код и тесты небольшими шагами. Каждый дифф я читал перед тем, как принять.
3. Готовность определялась так: `go test -race`, `tests/happy_path.py` против поднятого сервиса,
   live-тест кабинета против настоящего Go API и ручной проход сценария в UI под каждой ролью.
4. После первой версии я попросил Claude сделать ревью по заданию и сам дополнил его результаты (см. «Ревью и
   доработки»).

## Решения, принятые мной

| Решение                                                               | Почему                                                                                                                                                                                    |
|-----------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Деньги в `int64` минорных единицах, `profit × share` через `math/big` | Без `float` и внешнего decimal; `big.Int` убирает переполнение. Граница `9·10^15` ниже `Number.MAX_SAFE_INTEGER`, поэтому JSON безопасно читается в браузере.                             |
| Метод наибольших остатков, ничья решается по `investor_id`            | Сумма выплат всегда равна прибыли, результат детерминирован и не зависит от порядка вкладов. Смещение в пользу ранних ID — не больше одной копейки, это задокументировано в ARCHITECTURE. |
| Агрегат `Problem` одним JSON-документом в SQLite                      | Атомарность агрегата при минимальной схеме. Цена (нет SQL-отчётов по вкладам) записана в README.                                                                                          |
| Transactional outbox вместо публикации из кода команды                | Нет ни события без изменения, ни изменения без события. Это же путь к брокеру без правки домена.                                                                                          |
| Ключ операции у вклада                                                | Повтор после таймаута не должен удваивать деньги. Два одинаковых вклада одного инвестора — законный случай, поэтому сумма ключом служить не может.                                        |
| Распределение без ключа: ключ идемпотентности — сам пул               | Распределение одно на пул, так что та же прибыль — тот же факт.                                                                                                                           |
| Фильтрация видимости на сервере, отдельная read-модель                | UI вообще не получает чужих данных и ключей операций, а не просто их не показывает.                                                                                                       |
| Fiber v3, React/Vite                                                  | Привычный стек, быстрее довести до рабочего состояния.                                                                                                                                    |

## Ревью и доработки

Ревью по заданию сделал Claude по моему запросу. Оно нашло UX-баг у технолога, мёртвый код, слабый NOTES
и историю коммитов. **Три проблемы контракта ревью пропустило, их нашёл я:**

- `/profit` требовал ключ операции, хотя распределение одно на пул. Та же прибыль с новым ключом давала
  409, запрос без ключа — 422. Проверяющий с curl `{"amount":100000}` сразу упёрся бы в ошибку.
- Ключ идемпотентности клиента попадал в payload `ProfitDistributed` и в представления региона и эксперта.
  Это деталь транспорта, а не часть контракта события.
- Команды возвращали только `problem_id`, поэтому даже начисления клиент узнавал повторным `GET /api/state`.

Исправлено отдельными коммитами в обоих репозиториях:

| Проблема                                                                                        | Исправление                                                                                                     |
|-------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------|
| Технологу, чьё решение не выбрано, показывалась форма «Предложить решение», отправка давала 409 | Read-модель `ProblemView` с признаком `matched`: приём закрыт, но не видно, чьё решение выбрано                 |
| Обязательный ключ у `/profit`                                                                   | Тело `{"amount"}`; повтор той же суммы — no-op, другая сумма — 409                                              |
| Ключ в событии и представлениях                                                                 | Ключи только в агрегате, для дедупликации; тесты проверяют отсутствие `"key"` во всех представлениях и событиях |
| Команды отдавали только `problem_id`                                                            | Возвращают созданную сущность (у `/profit` — выплаты) и `replayed`                                              |
| Мёртвый `validation.Text`                                                                       | Удалён                                                                                                          |

На чём Claude пришлось поправлять уже в ходе доработок:

- Он предложил убрать ключ из JSON-ответа тегом `json:"-"`, но агрегат сериализуется тем же
  `json.Marshal`, так что ключ стёрся бы и из базы, и защита от повторов сломалась бы. Поэтому сделана
  отдельная read-модель.
- В README он описал `total` в ответе на вклад как «сумму на момент вклада». На повторе возвращается
  текущая сумма пула, формулировку исправили.

## Что предлагал Claude и я отклонил

- Kafka вместо in-process шины: для одного bounded context это избыточно, путь к брокеру описан в ARCHITECTURE.
- Hyperledger Fabric / Solidity: вне рамок задания; движок написан так, чтобы переноситься в chaincode.
- JWT: для take-home достаточно заголовков с проверкой по сидам.

## Что проверял сам

- `go vet`, `go test -race ./tests/...`, `python3 tests/happy_path.py` против поднятого compose.
- `npm test`, `npm run test:live` (React → Vite proxy → Go API).
- Прошёл happy-path в UI под каждой ролью, включая «чужой» регион, второго технолога и третьего инвестора.
- Вручную сверил выплаты 60 000 / 40 000 и то, что повтор распределения их не удваивает.
