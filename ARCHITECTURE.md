# Архитектура

## Границы сервиса

Сервис покрывает один bounded context: **«Инвест-пул региональной проблемы»**. Внутри него проходит путь от публикации
проблемы до автоматического распределения прибыли. Агрегат — `Problem`. Он владеет решениями, матчем эксперта, пулом,
вкладами и распределением.

```
Problem ──< Solution
   │
   ├── Match (одно, подтверждает эксперт)
   └── Pool (один, после Match)
         ├──< Investment
         └── Distribution ──< Payout
```

Жизненный цикл пула: `open` → `funded` (собрано ровно `target`) → `distributed`.

Каждая команда выполняется как одна транзакция над агрегатом: прочитать, проверить инварианты, записать агрегат и
событие в outbox. Инварианты «не больше цели», «вклад только после матча» и «распределение один раз» проверяются внутри
транзакции, поэтому их нельзя обойти гонкой. Это покрыто тестом `TestConcurrentInvestmentsAndProfit` с `-race`.

Вне границ остаются:

- учётные записи и аутентификация (здесь вместо них сиды);
- каталог технологий и поиск матчей;
- платёжный контур (здесь фиксируются начисления, переводов нет);
- уведомления и аналитика.

С остальной платформой сервис общается только событиями. Чужих таблиц он не читает.

Хранение: SQLite, по одной строке на агрегат (`problems.document`, JSON), плюс таблицы `outbox` и `audit`. Для среза это
минимизирует схему и гарантирует атомарность агрегата. При переходе на Postgres вклады и выплаты выносятся в отдельные
таблицы, а одновременная запись разных инстансов защищается полем `version` с оптимистичной блокировкой. Сейчас её роль
выполняют глобальный mutex репозитория и одно соединение с БД, что рассчитано на один инстанс.

## «Смарт-контракт»: движок в коде вместо Fabric

Распределение выполняет функция `services.Allocate(investments, profit) → payouts`. Регион только вводит сумму прибыли.
Разбиение по инвесторам и запись выплат происходят в той же транзакции, без ручного шага.

Почему код, а не Fabric или Solidity:

- **Задача требует свойств контракта, а не сети.** Нужны детерминизм, отсутствие посредника в расчёте, идемпотентность и
  неизменность результата. Всё это достигается чистой функцией и транзакцией, и всё проверяется unit- и property-тестами
  за миллисекунды.
- **Сеть добавляет инфраструктуру, но не корректность.** Fabric даёт консенсус между независимыми организациями. В срезе
  с одним владельцем данных такой консенсус не с кем достигать.
- **Функция уже написана под перенос.** `Allocate` не зависит от времени, случайности, `float` и I/O. Итерация по `map`
  не влияет на результат, потому что выход сортируется. Ничьи разрешаются детерминированно. Это ровно те требования,
  которые Fabric предъявляет к chaincode, а chaincode Fabric пишется на Go.

Как это выросло бы до контракта в сети:

1. **Промежуточный шаг без блокчейна.** Хэш-цепочка в аудите: каждое событие хранит хэш предыдущего. К `Distribution`
   добавляется подпись сервиса. Любая сторона может пересчитать `Allocate` по опубликованным вкладам и сверить
   результат.
2. **Fabric.** `Allocate` и проверки из `InvestmentsService` и `DistributionsService` переносятся в chaincode почти без
   изменений. Состояние хранится по ключам `pool/{id}`, `investment/{pool}/{investor}/{key}`, `distribution/{pool}`.
   Ключ операции становится частью ключа состояния, и идемпотентность сохраняется. Политика endorsement подбирается под
   задачу, например подпись региона и оператора платформы. Chaincode эмитирует события с теми же именами, а этот сервис
   становится off-chain API и проекцией для чтения.

## События

### Доставка

Событие записывается в `outbox` в той же транзакции, что и изменение агрегата: нет события без изменения и нет изменения
без события. Фоновый диспетчер (`Bus.Run`) читает недоставленные записи в порядке вставки и вызывает подписчиков. Запись
помечается `delivered` только после успеха всех подписчиков.

Диспетчер просыпается в трёх случаях:

- по сигналу после коммита;
- раз в секунду для повторов;
- при старте, чтобы доставить хвост после падения.

При остановке выполняется финальный `Drain`. Доставка — **at-least-once**, порядок сохраняется в рамках одного инстанса.

Подписчик сейчас один — журнал аудита (`audit`). Его читает `GET /api/events` и показывает UI.

### Идемпотентность потребителя

У каждого события стабильный `id`, который генерируется один раз при создании и хранится в outbox. Потребитель обязан
дедуплицировать события по `id`. Аудит делает это через `INSERT OR IGNORE INTO audit(event_id, …)` с `event_id` в
качестве первичного ключа, так что повторная доставка не создаёт дубля. Для потребителей с побочными эффектами
(уведомления) применяется тот же приём: таблица `processed_events(event_id PRIMARY KEY)` вставляется в одной транзакции
с эффектом (inbox pattern).

Отдельно от этого идемпотентны сами команды: повтор вклада или распределения с тем же ключом не создаёт нового события.
Поэтому дубли возможны только на уровне доставки, а не на уровне бизнес-факта.

### Рост до Kafka / RabbitMQ

- `Bus` заменяется relay-процессом: отдельная горутина или Debezium читает `outbox` и публикует в брокер. Доменный код
  не меняется, потому что он и сейчас пишет только в outbox.
- **Kafka.** Топик `invest-pool.events`, ключ сообщения — `problem_id`. Так сохраняется порядок событий одного агрегата
  внутри партиции.
- **RabbitMQ.** Topic exchange `invest-pool`, routing key — имя события. Каждый сервис заводит свою очередь.
- Потребители:
    - сервис уведомлений (`InvestmentAccepted` → инвестору, `ProfitDistributed` → всем участникам);
    - аналитика (воронка «проблема → матч → пул → прибыль» по регионам);
    - платёжный сервис (`ProfitDistributed` → исполнение выплат).

  Каждый потребитель ведёт свой inbox по `event_id`.
- В конверт нужно добавить `event_version` (эволюция схемы) и `sequence` агрегата (проверка порядка у потребителя), а
  доставленные записи outbox — периодически чистить.

### Контракт событий

Конверт события:

```json
{
  "id": "…",
  "name": "InvestmentAccepted",
  "problem_id": "…",
  "occurred_at": "2026-11-03T12:00:00.000Z",
  "payload": {}
}
```

| Событие              | Когда публикуется                                             | Payload                                                                                 |
|----------------------|---------------------------------------------------------------|-----------------------------------------------------------------------------------------|
| `ProblemPublished`   | регион опубликовал проблему                                   | `region_id`, `title`                                                                    |
| `SolutionProposed`*  | технолог предложил решение (до матча)                         | `id`, `technologist_id`, `description`                                                  |
| `SolutionMatched`    | эксперт впервые подтвердил матч; повтор события не создаёт    | `solution_id`, `expert_id`                                                              |
| `PoolCreated`*       | регион-владелец открыл пул после матча                        | `pool_id`, `target`                                                                     |
| `InvestmentAccepted` | вклад принят (новая пара «инвестор, ключ»; не сверх остатка)  | `pool_id`, `investment_id`, `investor_id`, `amount`, `total` (собрано после вклада)     |
| `ProfitDistributed`  | прибыль зафиксирована и распределена движком; один раз на пул | `pool_id`, `distribution`: `id`, `key`, `profit`, `payouts[]` (`investor_id`, `amount`) |

\* Дополнительные события сверх минимального контракта. Они нужны для полноты аудита.

Все суммы — целые минорные единицы. Событие публикуется только после успешного коммита изменения состояния. Отказы
(`4xx`) событий не порождают.

## Правило округления денег

Используется **метод наибольших остатков** (Hamilton) в целых числах:

1. Вклады одного инвестора суммируются: `share_i`, `total = Σ share_i`.
2. Базовая выплата `q_i = ⌊profit × share_i / total⌋`. Произведение считается в `big.Int`, поэтому переполнения нет при
   любых суммах до `9·10^15`.
3. Остаток `r = profit − Σ q_i` всегда меньше числа инвесторов. Он раздаётся по одной минорной единице инвесторам с
   наибольшим остатком деления `(profit × share_i) mod total`.
4. **Ничья** по остатку разрешается по `investor_id` в лексикографическом порядке.
5. Результат сортируется по `investor_id`.

Гарантии правила:

- `Σ payouts = profit` (проверяется тестами);
- результат не зависит от порядка вкладов (проверяется тестами);
- каждая выплата равна `⌊точная доля⌋` или `⌊точная доля⌋ + 1`, то есть отличается от точной доли меньше чем на одну
  минорную единицу. Это следует из метода; отдельного теста на это свойство пока нет.

Примеры:

| Доли                | Прибыль | Выплаты         | Пояснение                                                    |
|---------------------|---------|-----------------|--------------------------------------------------------------|
| 600 000 / 400 000   | 100 000 | 60 000 / 40 000 | делится без остатка                                          |
| 1 / 1 / 1 (a, b, c) | 2       | 1 / 1 / 0       | равные остатки, единицы получают a и b по ID                 |
| 1 / 2               | 2       | 1 / 1           | точные доли 0,67 и 1,33; у меньшего вкладчика остаток больше |

Известное свойство правила: при ничьих выигрывают ID, раньше идущие по алфавиту. На суммах в копейках эффект ограничен
одной минорной единицей на распределение. Если потребуется нейтральность, ничью можно разрешать по времени первого
вклада или по хэшу `(distribution_id, investor_id)`. Детерминизм при этом сохраняется.
